# 端到端测试：测试依赖的浏览器事实

文中“实测”的结论，日期和测法：未记录。

Vitest + `puppeteer-core`，驱动本机安装的 Google Chrome 和 Firefox（可用 `CHROME_PATH` / `FIREFOX_PATH` 覆盖；缺少对应浏览器或构建产物时，该套测试会自动跳过）。共享的辅助代码在 `e2e/support/`；所有临时 profile、下载文件和打过补丁的构建副本都放在系统临时目录下，每个测试文件结束后删除。测试依赖下面这些事实，原因如下：

- **遮罩**（`e2e/cover.e2e.ts`）：遮罩默认关，开启要授予可选的“所有网站”权限，headless 下点不了权限确认框，所以 `launchChrome` 用的构建副本（以及遮罩测试自己打补丁的副本）带 `grantPageAccess`：把 `optional_host_permissions` 挪进 `host_permissions`，安装时就授予；测试再用 `turnCoverOn` 写 `prefs.cover` 并等后台注册好网页脚本。设置里的遮罩开关也能直接点：权限已经有了，`permissions.request` 不弹框、直接返回 true；但它要求用户手势，所以 `setSwitch` 用真实的鼠标点击，不能在页面里调 `click()`。另有一组用未打补丁的构建（只留 zh_CN）检查发布出去的样子：安装时没有网站权限、manifest 里没有 `content_scripts` 和 `host_permissions`，开关开着却没权限时后台把它写回关；别的套件都持有权限，权限要是又变成必需的，它们发现不了。弹出权限框、`onAdded`/`onRemoved` 跟随这两条路径只能手动验收。Chrome 对 history API 跳转也报 `status: 'loading'`；纯 http 页面跳转后，网页脚本消息的 `sender.url` 仍是跳转前的地址（后台据此答“不受保护”），所以测站内跳转被遮住要用 `localhost`。遮罩是用 `showModal()` 打开的 `<dialog>`，测试用 `:modal` 判断是否遮住，按视口中心点击“显示页面”（按钮在封闭的 shadow root 里）。测试服务器是纯 http，走“问后台”的路径；`http://localhost` 是安全上下文，用来覆盖网页脚本自己算哈希的路径。窗口失焦用 `chrome.windows.onFocusChanged.dispatch(WINDOW_ID_NONE)` 模拟。无操作计时和“播放中不计时”在一份打过补丁的构建副本里测（`patchedCopy` 的 `pageScript` 把网页脚本（`scripts/cover.js`）里的一分钟换成一秒、静音宽限期换成 1.5 秒，并核对替换次数，构建产物变了会直接报错）；声音来自一个远低于听觉的振荡器（17 kHz、-60 dB），为此这组测试用 `launchChrome({audible: true})` 去掉 puppeteer 默认的 `--mute-audio`（带着它，标签页永远不会变成 `audible`）。
- **Chrome**：用 `puppeteer.launch({pipe: true, enableExtensions: [dist/chromium]})` 和全新 profile。扩展 id 从 service worker target 获取；`sw.evaluate()` 可以在 background 里调用 `chrome.*`。popup 界面以标签页形式驱动，地址是 `chrome-extension://<id>/action/index.html`（关闭标签页 = 关闭 popup）。`--host-resolver-rules=MAP * 127.0.0.1:<port>` 加上 `e2e/support/server.ts`，让 `example.com` 等成为真实访问并进入历史。panic 用 `chrome.commands.onCommand.dispatch('panic')` 触发。
- **真实 popup**（`e2e/real-popup.e2e.ts`，仅在 `E2E_HEADED=1` 时运行）：先聚焦一个普通窗口，再从 service worker 调用 `chrome.action.openPopup({windowId})`。它固定住了界面设计所依赖的几个事实：文件选择器**不会**关掉 popup（macOS 上的 Chrome）；blob 下载在 popup 关闭后仍能完成。（`permissions.request` 的弹窗**会**关掉 popup——这就是 `bookmarks` 是必需权限的原因。）
- **Firefox**：WebDriver BiDi 能安装附加组件（`browser.installExtension`），但拒绝导航到或暴露 `moz-extension://` 页面，所以没法驱动 popup 界面。`e2e/firefox-history.e2e.ts` 改为检查 background：一个打过补丁的副本预置匹配表，访问通过测试服务器（作为 HTTP 代理）进行，关闭浏览器后用 `sqlite3` 命令行读取 `places.sqlite`，看历史里还剩什么。只在 popup 里的 Firefox 分支（粘贴式备份导入）仍需用 `pnpm dev:firefox` 手动过一遍。
  - **启动方式**：用 `e2e/support/firefox.ts` 的 `launchFirefox`。macOS 上它用 `open -W -n -g -a Firefox.app --args …`（由 launchd 拉起）启动 headless Firefox，profile 由 `@puppeteer/browsers` 的 `createProfile` 写好（和 `puppeteer.launch` 写的一样，带自动化默认首选项），连接地址（`ws_host` / `ws_port`）从 profile 里的 `WebDriverBiDiServer.json` 读，再 `puppeteer.connect`；`close()` 等 `open -W` 退出，确保 `places.sqlite` 已写完（10 秒等不到、或连接已经断了，就用 `pkill -f` 杀掉再等 5 秒，仍不退出就对 `open` 调 `unref()` 并报错。puppeteer 的 BiDi `browser.close()` 自己吞掉错误，所以连接是否断开要事先查 `browser.connected`）。`pkill` 的模式锚定在 `^<Firefox.app>/… --profile <路径>`，只杀 Firefox、不碰 `open`，杀掉后照旧等 `open -W` 退出。`open` 会改写自己的 argv（`ps` 里看不到 `--profile`），别指望按 profile 路径能匹配到它。启动失败时也同样杀掉并等它退出，免得删临时 profile 时撞上还在写的 Firefox。`open` 提前退出时立刻报错，不空等 30 秒。macOS 上 `FIREFOX_PATH` 必须（解析软链后）是某个 `.app` 或落在它里面，否则直接报错。其他系统仍用 `puppeteer.launch`。
  - **为什么不直接 `puppeteer.launch`**：2026-11 升级到 macOS 27 后，从 Claude Code 的进程树里启动的 Firefox（154）读不到自己的 `~/Library/Application Support/Firefox`（从这里 `ls` 该目录也报 Operation not permitted，Chrome 的 `Google` 目录不受影响），会停在“找不到 profile”对话框上；headless 时对话框不显示，进程空转、profile 里一个文件都不写，puppeteer 30 秒等不到 WS 地址而超时。换 `--profile` 位置、换 `HOME`、不加远程调试参数都一样；同样的参数经 `open` 启动就正常。是哪一项系统权限拦的没有查实。
- **语言**：界面操作按 zh_CN 文案查找按钮（`clickText`）。为了不让本机语言把它们切成英文，`launchChrome` 加载的是一份只有 zh_CN 语言包（同时也是默认语言）的构建副本。只有 `e2e/locale.e2e.ts` 传 `lang` 并运行真实构建，检查 en-US / zh-TW / zh-CN / zh-HK / ja 浏览器分别得到哪种语言。macOS 上的 Chrome 会忽略 `--lang`；`-AppleLanguages (xx)` 在那里有效，但也会打开一个多余的 `http://(xx)/` 标签页，所以历史/标签页相关的测试里不要用它。
